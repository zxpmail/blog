# Agent 记忆里什么该留、什么该扔——以及为什么这件事比想象中难

同题旧稿的原则这版收成可操作的机制草案，并标明证据边界。（旧稿硬伤备忘见文末。）

目标读者：搭 Agent 记忆系统的人。文中不解释基础概念，但每处结论都标了前提和适用范围。非工程读者可只看「记对了，后来用歪了」和「三层会移动」两节。

核心两句：Agent 记忆的矛盾主要是可信度，不是容量。垃圾不是「没用」，而是「复用时被当成知识，却已不成立或已过时」。难点不在分类，在记忆会变质。

## 先钉词

「元数据」在本文里不是数据库字段说明，而是长期、默认被系统优先信任的规则层（系统提示、全局手册等）。升格到元数据 = 进这一层。

元数据至少四类：安全约束、经验规则、环境默认假设、表示结构。前两类本文展开；后两类文末用一段对齐，不另起炉灶。

## 记对了，后来用歪了

月见山类翻车足够说明机制：会话里记下「中心在 A」，当时地图支持它，条目被升成经验甚至写进手册；地图变了仍按手册走，就失败。若只对旧笔记再概括，错会被压得更像公理。要纠，只能回原始执行记录——当时看见了什么、凭哪次观察写下 A——再降级、改条件，或标成「已推翻」。

骨架就这一条：会话 →（有证据）经验 →（审批）元数据；环境一变，要能降级、过期、回原始记录。分类表解决不了变质。

## 无条件规则：先分清是约束还是经验

「没有适用条件 = 半成品」说过头了。安全约束（不可逆先确认、不泄密钥）可以无条件，稳定性来自设计。经验规则（报错先重试、改代码前先读文件）必须带条件，否则易过度泛化。

维护也要拆开：约束审设计还成不成立；经验审条件还盖不盖得住现场。

## 四条判据：排序 + 例外

打架时粗排：可验证性 → 条件清晰 → 可复用性 → 可检索性。

没证据的可记，只能当「待验证」，禁止当规则用。写不出条件的进案例库，不自动套用。只对当前任务有效的留会话层。检索成本决定清不清理，不单独决定能不能存。

例外：高危安全约束应在完整经验验证之前就生效——走设计通道。排序管经验升格，不管「把涌现经验升成约束」这种偷换。

## 派生结果：比推导成本，不搞一刀切

「可推导就不存」太绝对。推导便宜且稳定 → 每次算。推导贵或依赖外部状态 → 可存，必须带过期。重算易错 → 存成缓存，读时先校验。规则是生成器；缓存是快照。没有失效机制的快照，就是未来的垃圾。

## 三层会移动

会话仍成立且有证据 → 经验；只服务当前任务 → 留会话并清理。待验证条目多次成立且条件清楚 → 经验规则；被证伪 → 留作反例。经验规则要进元数据 → 只能候选，必须审批；条件失效 → 降级或过期。安全约束型元数据只随设计变更，人工审，禁止自动升格。

降级和过期是常规，不是事故响应。对旧笔记再概括，不是纠错。

## 频率和周期：没有普适数字，但有定法

「多次」「定期」「环境变了」若只留字段不说怎么定，落地会卡死。这里没有行业标准答案，只有可执行的定法——数字要你们按风险自己填。

「多次验证」：先在复审条件里写下最小次数 n 与窗口，禁止口头「多次」。脚手架默认可以写成「n≥3 次独立任务且无反例」，**3 只是占位，不是推荐值**；高危操作加大 n，或改成必须人工点头。

「跨任务反复成立」：任务要有可区分的任务 ID 或场景标签；同一会话里连点三次不算三次。至少覆盖两个场景标签，再谈升格候选。

「定期复审」：按失效代价选周期。低代价经验可以按自然周/迭代扫；一写进元数据的经验规则，周期应短于你能忍受「带着错规则跑」的最长时间。复审产出只有三选一：保留、降级、标过期——不许只「看过」。

「环境变更」怎么检测：不要幻想模型自己「感觉到了」。至少接一类外置信号——配置版本、工具 schema hash、权限集、数据快照号、或人工声明的 domain 切换。信号变了，触发相关条目复审；没有信号源，就承认你做不到自动降级，只能缩短定期复审。

过期时间同理：缓存类按外部状态的刷新节奏定；经验规则的过期是「最迟何时必须复审」，不是「到点自动变真理」。

## 元数据：怎么存、谁批；后两类怎么挂

进元数据层至少有：内容、类型、依据、复审条件（含过期/信号）。

谁批：安全约束——只随设计变更，人工审。经验规则——Agent 可提议，必须附证据链，人工或独立评审批；禁止自动升格。

环境默认假设（如「默认时区」「默认集群」）：当经验规则走同一套条件、证据与审批；它比安全约束更易随部署变，复审条件里必须挂配置/环境信号。表示结构（目录约定、ID 格式、笔记模板）：默认当设计产物，变更走设计审；若由使用中涌现再固化，先当经验规则候选，审批通过后才能写进元数据。后两类按经验规则走同一套审批，差别只在复审信号源。

信号缺失时的退化，要提前说清：如果连环境变更都检测不到，那么「失效代价」往往也估不准，状态机的降级分支实际退化成「靠人定期看一眼」。这不是设计失败，是前提缺失——在这种情况下，状态机不提供自动保障，只提供记录格式和人工检查的入口。别把「有状态机」误当成「自动可信」。

## 初筛

按上面的判据排序走一遍即可，检查项不另起一套逻辑：

还有用吗？无 → 不升格。有证据吗？无 → 待验证。约束还是经验？约束 → 人工审。条件写清了吗？写不出 → 案例库。能推导吗？能 → 比成本再决定是否缓存。来自几次任务？单次不进规则层；达到你们写下的 n 则附证据链进审批。Agent 报告次数即可，不必自判「是不是涌现」。

## 收束

长期可用至少三样：结构化条目；有审批的升格与当作常规的降级/过期；回原始记录的纠错路径。

值得留的：能安全复用的生成规则、带条件的验证经验、有失效机制的缓存。该扔的：一次性上下文、未验证猜测、无边界经验、没有过期的派生快照。

难点不是把库做大，是让记忆在升格、降级、过期、纠错里仍可信。

**折扣（请和正文一起读）：** 这是有边界的机制草案，不是生产评测报告。实验只证明旧记忆会被迟钝复用，不证明状态机能防住；N=5、单模型，不加统计外推。频率与周期只有定法、没有普适常数；文中的 n=3 是脚手架占位。信号源缺失时自动降级不可用，这一点比方案本身更值得先确认。有「存时对、用时坑」的实录，比再画架构图有用。
