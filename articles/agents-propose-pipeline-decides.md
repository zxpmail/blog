# 为什么说“让 AI 搭企业系统”之前，必须先建一条审批管线
——写给确定要持续生产多类业务系统的组织

我们在做 DAF（Domain Application Foundation，领域应用基座）——一个企业级“业务系统工厂”。这篇文章讲清楚它的核心判断：业务系统不该是被开发出来的应用，而该是一份份可版本化、可审批、可回滚的声明式蓝图；agent 可以组装蓝图，但必须走一条有人守门的管线。

文章不只讲设计，也会把每一步的代价摊开讲。

本文定位：设计假设 + 一次端到端演练的复盘，不是生产验证结论。哪些有测试、哪些还只是方向，文中逐节标注，并在第三节末附一张证据状态表。

## 一、从一个老问题说起

做过企业信息化的朋友大概都见过这个循环：

业务方要一个新系统（工单、进销存、项目管理……）；技术团队从零搭一套：登录、权限、组织架构、菜单、CRUD、报表、流程引擎……三个月后上线，第二个需求来了，再搭一套；五年后，公司里有 30 套系统，30 套用户表，30 种权限模型，谁也不敢动。

市面上的低代码平台试图解决这个问题，但大多数把“快”建立在“黑盒”上：模型不可迁移、权限不可定制、和平台强绑定。而另一边，Agent / LLM 的兴起让“AI 帮你搭系统”成为可能——但只要想象一下 agent 直接在生产库上执行它“组装”的结果，就知道企业真正需要的是既能被 AI 组装、又能被人治理的底座。

DAF 的答案是：把“构建一类业务系统”所需的通用能力抽象成一个组件式、可拼装的基座；业务系统 = 基座 + 一份声明式蓝图。

先看这份蓝图长什么样。这是一份真实存在的工单系统示例蓝图（按 daf.blueprint.v1 schema 编写、用于管线校验测试）：

```json
{
  "apiVersion": "daf.blueprint.v1",
  "name": "ticket-intake",
  "version": "1.0.0",
  "entry": "/tickets/new",
  "entities": [{
    "apiVersion": "daf.entity.v1",
    "type": "ticket",
    "tenantIsolation": "row",
    "auditFields": true,
    "fields": [
      { "name": "title", "type": "string", "len": 200, "required": true },
      { "name": "status", "type": "enum", "enumValues": ["open", "done"], "required": true }
    ]
  }],
  "pages": [{
    "apiVersion": "daf.page.v1",
    "route": "/tickets/new",
    "layout": "form",
    "blocks": [{ "block": "form", "data": { "kind": "entity", "ref": "ticket" } }]
  }],
  "flows": [{ "key": "intake", "definitionRef": "sha256:demo" }]
}
```

数据模型、页面、流程在一个文件里，可签名、可版本化、可回滚。一个最小工单系统的全部定义，不超过 40 行。

**这 40 行能走多远，先把丑话说透**：它覆盖的是“长得很像”的常规场景——表单、列表、审批流。按我们内部复盘历史需求的估计，这类场景占大头；但这是估计，不是统计数字。剩下那些长不一样的——计费规则、跨系统对账、奇怪的审批特例——终究要落回受控的代码插槽。

**插槽是这套方案最可能死掉的地方，所以单独说**：历史上决定这类平台成败的，往往不是蓝图声明有多优雅，而是用户撞上插槽那面墙之后的调试、测试、版本化体验。目前的机制只有一条：插槽的版本化随蓝图走；供应链校验（来源签名、依赖审计）还只是方向、不是机制。我们能拿出的对冲也很诚实：把它标为最高风险项，交给第一个真实项目去锤——插槽体验成不成，最终由那个项目裁决，不由这篇文档裁决。

## 二、架构：一个内核 + 三张平面

```text
组装平面：组装工作台（人工）+ 语义注册表（agent 面）+ 组装管线
    ↓ 发布/回滚（不可变制品）
制品平面：蓝图 · 语义卡 · 模板 · 实体 schema —— 一切皆制品、皆版本化
    ↓ 实例化/装载
运行平面：网关 + 核心服务 + 数据服务 + 前端外壳，自持全套基础设施
```

（名词一件事：**语义卡**是把一个业务概念——字段口径、指标定义、术语——写成可版本化、可被 agent 按语义检索的制品；页面和流程通过引用使用它，而不是各自复制一份定义。）

组装平面是灵魂。蓝图从草稿到上线要走一条受控管线：

```text
draft → static-validate → guard（策略/安全护栏）
      → preview（沙箱预览）→ approve（审批）→ publish → 可 rollback
```

agent 可以提组装方案，但能不能过，由 guard 说了算。以实际规则为例：蓝图 diff 出现删实体、删字段、类型或宽度变更（判定口径是存量数据兼容性：string→int、缩短长度、删枚举值可能让已有数据失效，算收紧；int→string 不会，算放宽）时，guard 会遍历引用图谱给出影响面报告——哪个页面绑定着这个字段、哪条流程、哪张语义卡——然后 veto：管线终止，HTTP 403，findings 完整回执。护栏策略可按租户配置，但只能收紧、不能放宽；规则引擎自身抛异常也按 block 处理——失败关闭。回滚同样要重过破坏性检查，在途流程实例钉住其启动版本。

一句话总结这一节：让 agent 提方案，让管线守底线。没有这条管线的“AI 搭系统”，在需要审计和追责的企业环境里，大概率停在演示阶段。

几个机制的已知边界，也一并交代：

- **guard 的策略表达力有限**（规则集五组），复杂业务红线仍要靠 L3 人审兜底。
- **误杀的申诉与放行**：findings 全量留痕，同一规则在不同 run 的历史裁决可对比；destructive 类策略的变更本身要双人确认。这里有个粒度缺口——现在的放行手段是“改策略”，粒度在策略、不在单次变更；对单个变更登记例外（限期、留痕）的例外审批通道还没建。
- **审批 SLA 目前没有定义**（这是诚实的空白），当前由租户侧流程制度兜底；管线只保证会签语义和留痕，SLA 是后续要补的运行指标。
- **还有一个没解决、也不打算假装解决了的问题——回滚与数据前进的互锁**：假设 v2 给实体新增了一个枚举值、已有数据用了它，此时发现 v2 有致命缺陷要回滚——从 v1 蓝图看，“删掉这个枚举值”正是 guard 要拦的收紧变更。也就是说，你最需要回滚的时刻，恰好是 guard 最可能拦住你的时刻。蓝图可回滚不等于数据可回滚；业界对应模式是 expand-contract（先扩不缩、数据清洗前置），它以什么形态进 guard 的放行路径，还没有设计定案。
- **蓝图复用**靠模板实例化 + 升级 diff 重放，没有完整的蓝图继承体系——这是刻意为之（继承层级是低代码平台长成黑盒的主要路径之一），代价是跨蓝图的共性提取要靠人工。

先把丑话说在前面——这套东西适合谁、不适合谁：

| 适合 | 不适合 |
|------|--------|
| 确定要持续生产多类业务系统的组织 | 只做一两个系统的团队（直接用脚手架） |
| 有平台运维能力（能扛一个中型微服务集群） | 没有平台团队、想把运维全部外包的组织 |
| 强治理要求：审计、合规、等保、多人审批 | 演示、PoC、追求最快出活的场景 |

两个值得一提的执行层设计：

**权限编译进执行计划**：行级权限在查询编译期注入（Hasura 模式）+ PostgreSQL RLS 双保险，不做结果集后过滤。这是为了一个朴素目标：agent 走 MCP 工具查数据和人走页面查数据，被同一套权限规则约束，没有旁路。

**协议防腐**：一切外部协议止于 adapter / bridge 层，核心元模型协议无关。

## 三、目前最接近“案例”的东西：一次端到端演练

先坦白：DAF 还没有生产租户，所以没有“从 draft 到 publish 走了三天、误杀率 5%”这种数据。把必然的反问先自己问掉：**你们自己的内部系统跑在 DAF 上吗？也没有——“没有生产租户”包括我们自己。** 第一个真实租户应该轮到我们自己的工单和项目管理；在那之前，第三节末的证据状态表有一个明摆着的洞——“生产验证”整列未验证，我们认。

目前最接近案例的，是一次跑通全链路的自动化端到端演练（AssemblyStudioS1E2ETest，DS4 阶段出口证据），值得原样讲一遍，因为它把管线的主要承诺过了一遍：

- 路径：从模板起步 → 定制 → L0 校验 → L1 guard → L2 沙箱预览 → L3 审批 → L4 发布 → 升级 → 回滚，全链路走完；
- guard 真拦了东西：删字段被 veto 且带影响面回执；顺带验证了字段类型变更、删页面、改数据绑定同样会被 block——比设计承诺拦得更宽；
- 审批真有门槛：高风险变更要求至少 2 个审批人分别表态，单人说了不算；
- 回滚真发生过：发布时语义卡发布失败，补偿逻辑真实调用了回滚——应用退回上一版本，而不是停在半成品状态。另有一条铁律在同一批测试里验证：管理员想绕过管线直接装制品，被 403 拒绝——管线无绕过。

周期长什么样：机器侧（L0 校验、L1 guard）是确定性检查，毫秒到秒级，成本固定、可复算；draft→publish 的真实墙钟时间由 L2 预览启动和 L3 人审主导——瓶颈在人和预览环境，不在管线本身，这正是 SLA 空白为什么必须补。需要说明：这一段是设计判断，不是实测数字；没有可引用的分阶段计时，就不报数——这是全文的口径。

同样诚实的边界：L2 预览的抽样数据目前是合成数据而非生产实体行；审批只接了高风险会签的语义，全量审批流未接；模板目录还是代码种子。这是一次演练，不是战绩——但“主要承诺都有对应测试”这件事本身，就是这篇文章敢写这么多机制细节的原因。

证据状态一览（✅=有对应实现；◐=部分；○=未验证）：

| 机制 | 设计 | 实现 | 测试 | 生产验证 |
|------|------|------|------|----------|
| guard veto / 影响面回执 | ✅ | ✅ | 演练通过* | 未验证（无生产租户） |
| 回滚补偿 / 在途实例钉版本 | ✅ | ✅ | 演练中触发* | 未验证 |
| 高风险会签（≥2 人） | ✅ | ✅ | 演练通过* | 未验证 |
| 管线无绕过（403） | ✅ | ✅ | 演练通过* | 未验证 |
| 权限编译期注入 + RLS | ✅ | ◐ | ◐ | 未验证 |
| 策略缓存秒级失效 | ✅ | ◐ | ○ | 未验证 |
| 审计哈希链 | ✅ | ◐ | ○ | 未验证 |
| Agent OS 互操作 | ✅ | ◐ mock | ◐ mock | 未验证 |

\* “测试”列指自写的端到端演练通过——不是第三方验证，更不是生产验证。

## 四、和 Agent OS 的关系：整体协作，而非模块级纠缠

DAF 可以接入外部 Agent OS 获得“智能组装”能力，但两者之间只有四条系统级开放协议通道：

| 通道 | 方向 | 协议 |
|------|------|------|
| 任务通道 | DAF → Agent | A2A / REST |
| 工具通道 | Agent → DAF | MCP（DAF 作为 MCP Server） |
| 事件通道 | 双向 | CloudEvents over HTTPS webhook |
| 身份通道 | 双向 | OIDC + Token Exchange（RFC 8693） |

全部是开放协议，契约版本化冻结。替换接入的设计目标是“新写一个 Adapter、DAF 核心零改动”——互操作测试尚在补齐（真实对端联调还未做，当前验证基于 mock；“第二实现接入复跑用例”的证伪试验已列入出口条件但未执行）。拔掉 bridge 模块，DAF 就是无 Agent 模式，业务功能无损降级为人工组装——智能是增益项，不是依赖项。

关键是，“解耦”在这里不停留在口号：CI 硬门用一组封闭正则扫描 spec 和源码，命中数必须为 0；模块依赖图中所有指向外部的边只能汇聚于 bridge 一个节点，用 ArchUnit 在构建期强制。解耦是被机器验证的，不是被文档承诺的。

但这一节也有必须摊开的账单：为了“自持运行时、不共享任何中间件实例”，DAF 要自己扛一套 PG、Redis、RocketMQ、Keycloak、可观测栈。minimal 部署档压到了大约 13 个实例 / 14 vCPU / 42G 内存——这仍意味着你要自己运维一个小型平台。企业级洁癖是有价格的，客户环境里这条红线被反复挑战，我们也已经留了外接云托管服务的口子。

## 五、42 个模块，翻译成人话是什么

模块目录上写着 42 个模块、三档装配包。这个数字需要翻译：它意味着基座自身的复杂度约等于一个中型微服务集群，你换来的是蓝图的复用能力。

对复杂度，我们做了两件对冲：一是 45 条需求拆成 42 个模块、84 个服务键与事件，三张表由脚本自动对账——文档说谎，CI 会红；二是每个模块一份结构化 spec，颗粒度到“可以直接交给开发写代码”。设计侧的纪律我们自认做到了位——但纸面一致不等于跑起来一致。查询编译期权限注入、策略缓存秒级失效、审计哈希链这些点，只有代码和运行数据能证明。目前项目正处于把设计锤成运行证据的阶段，跑通的证据链还在一块块补齐，在这之前，请把这套设计当作“一套经过内部多轮评审的假设”，而不是“已验证的结论”。

这笔账还可以往决策再推一步：**回本点 ≈ 基座年持有成本 ÷ 单个系统省下的重复开发成本**。按我们的经验，这个点在 3~5 个系统之上——如果最终只承载三五个业务系统，基座的维护成本大概率盖过它省下的钱。这就是第一节适用框收得那么窄的原因。

## 六、为什么不直接用现成的方案？

这是评论区必然出现的问题，先自己回答。一张表：

| 方案 | 适合 | 不适合 DAF 场景的地方 |
|------|------|------------------------|
| 低代码平台（明道/简道/OutSystems） | 快速出业务表单和流程 | 模型不可迁移、平台黑盒、权限定制受限；agent 组装多数无治理通道 |
| Salesforce / ServiceNow（metadata 平台） | 成熟的 metadata 模型 + 企业级部署治理 + 生态与报表流程齐全 | 闭源、厂商锁定、按席位计费、模型不可迁出；深度定制回到平台闭源技术栈（Apex 等） |
| Frappe / Odoo（开源 metadata 平台） | 模型开放、可自持，ERP 场景生产验证充分 | schema 变更走迁移脚本，没有 guard 式影响面 veto 与会签发布管线；agent 接入是 RPC API、没有语义注册表这层受控组装入口；多租户按站点隔离而非行级 |
| Backstage / Port | 开发者门户、软件模板目录 | 管目录不管运行：没有数据层/权限层/组装管线，“模板”到“系统”之间仍要自己写 |
| GitOps + OPA（脚手架代码库 + CI + 策略引擎） | 团队有强工程文化、系统形态各异 | 治理对象是基础设施不是业务语义；蓝图、实体模型、语义卡这些业务制品层要全部自建 |
| 传统脚手架 | 一两个系统、小团队 | 第 2 个系统开始重复搭用户/权限/审计，正是第一节的死循环 |
| 纯 Agent 生成 | 原型、demo、一次性脚本 | 无审批管线、无制品版本化、agent 直接触碰生产环境——企业不可接受 |
| DAF | 持续生产多类业务系统 + 强治理 + 要 agent 可参与 | 上面各行的场景它都偏重；运维一个基座本身的成本见第五节 |

和最接近的两行多说一句：DAF 相对 Frappe/Odoo 的增量不在声明式模型——DocType 这类机制已经存在很多年——而在三件事：发布管线的治理（guard 影响面 veto 与会签）、给 agent 的受控组装入口（语义注册表）、管线无绕过。这三件恰好是开源 metadata 平台没替你做的。相对 Salesforce/ServiceNow，DAF 押的是模型开放与可自持，代价是没有它们的生态和多年生产打磨。

一句话：DAF 不是和这些方案比“好”，而是和它们比“窄”——它只押注“持续生产多类业务系统”这一种组织形态。如果你的场景命中上面任何一行（除 DAF 外），请诚实地选那一行。

## 七、写在最后

至少在我们押注的“持续生产多类业务系统”这个场景里，企业软件的未来大概率不是“一个更大的单体”，而是“一个能持续生产业务系统的工厂 + 一条被治理的智能组装管线”。DAF 是我们对这个判断的一次完整作答——外加上面每一节都没少浇的冷水。
