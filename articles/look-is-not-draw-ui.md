# 为什么你看了很多 UI 拆解，还是画不好页面

打开 Figma，第一笔不知道落哪。不是组件库没装全，是脑子里全是「怎么看完一个页面」，没有「怎么决定画什么」。

先说结论：大多数 UI 拆解文章，教的是「怎么看」，不是「怎么画」。

视觉层次、微交互、状态设计、信息架构，你背得再熟，也可能对着空白画板发呆。因为拆解是解释已有结果；创作是在一堆约束里做取舍。这两件事中间，隔着一整条上游决策链。

我不是反对拆解。拆解很有用。问题在于，很多人把评审框架当成了创作流程。于是出现一种很典型的失真：页面很精致，间距很讲究，动效也顺，但你说不清它服务哪个目标、哪个场景、哪个任务。

好看，是「看」过关了。别扭，是「画」的时候缺了上游。

## 「看」回答成立，「画」回答取舍

视觉层次、微交互、状态覆盖、信息架构，这四个维度基本是业界共识。它们确实能解释绝大多数「为什么这个页面用起来舒服」：

大小、颜色、间距、位置，把主任务和辅助信息分开；按压、加载、成功、失败，给状态变化即时反馈；空、错误、禁用、超时、权限不足，覆盖非正常态；分组、优先级、路径，让人快速找到目标。

但注意：这四个维度都是下游维度。

它们回答的是「画出来之后是否成立」，不是「该画什么」。你拿它们去评审一个已有页面，很好用；你拿它们从零定义 UI，就会变成用审美和组件库替产品做决定。

「看」是事后解释。「画」是事前取舍。把解释工具当成创作入口，顺序就反了。

## 没有上游，失真通常不止一层

UI 不是起点，是上游决策的视觉投影。没有愿景、客户需求、分析和原型结构，直接定义 UI，失真通常不是一种，而是五层：

目标失真：页面很精致，但不知道服务哪个业务目标。

场景失真：桌面端思维做移动端，或者把低频功能当高频入口。

结构失真：视觉层次漂亮，但任务路径绕，用户找不到关键操作。

状态失真：只画正常态，空、失败、超时、权限不足全漏。

视觉失真：强调色、间距、动效都在，但没有一个能回溯到上游决策。

举个很常见的例子：个人中心页。看起来只是「头像 + 列表 + 订单入口」，但它真正考验的是信息架构。订单区四个图标不是等权的，「待付款」「待收货」要放两端、要带角标；组间用 8px 灰色间隔条分组，比 1px 分割线更清晰。

这些不是「审美选择」，是任务优先级和触达效率的翻译。你如果不知道哪个任务是高频、哪个操作有风险，视觉上再怎么调，也只是局部精致、全局低效。

看懂了别人的个人中心，不等于你会画自己的个人中心。前者是复盘结果，后者是先排优先级。

## 正确顺序不是瀑布，是回路

逻辑顺序应该是：愿景 → 客户需求 → 分析 → 原型 → UI。

愿景决定「为什么做、为谁做、不做什么」，给 UI 定价值主张和边界。客户需求决定「谁在什么场景下完成什么任务」，给 UI 定任务路径。分析决定约束和优先级：业务流程、数据、技术可行性、合规、运营规则。原型决定信息架构、任务流和状态矩阵，给 UI 定骨架。

到这一步，UI 才是翻译：把任务优先级翻译成视觉层次，把状态转换翻译成微交互，把边界条件翻译成状态设计。

但这不是单向瀑布。原型和 UI 经常会反过来暴露上游没想清楚的地方。画状态矩阵时发现流程有断点，画信息架构时发现需求优先级打架。设计师主动用原型去质问上游，不是越位，是补位。

更现实的是，上游质量参差是常态。需求模糊、分析缺失时，设计师如果只会等「完整输入」，项目就卡死了。可行做法是：带着假设做粗原型，把假设显性化，再拉上游一起确认。UI 在这里不是执行，是验证工具。

所以「画」不是等上游交卷再开工，而是把上游没说清的部分，用线框和状态表逼出来。

## 顶尖 PM 能从愿景得到什么，得不到什么

有人会说：顶尖产品经理根据愿景就能得到所有东西。这话有一半对。

顶尖 PM 确实能从一个足够强的愿景里推导出大量决策。不是因为他会算命，而是因为愿景一旦清晰，就变成了一个取舍过滤器：为谁做、不为谁做；什么价值优先、什么可以牺牲；哪些是核心、哪些是边缘；成功指标怎么定、优先级怎么排。

这些方向性、原则性、优先级性的东西，顶尖 PM 确实能「从愿景得到」。他得到的不是细节清单，是一套判断标准。

但「得到所有」不成立。原因有三。

愿景是压缩，不是展开。它决定方向和原则，不决定具体交互和状态矩阵。「让支付更有安全感」能推出设计原则，但推不出支付失败是弹窗还是页内提示、风控拦截文案怎么写、余额不足要不要引导换卡。

细节依赖约束和发现。技术可行性、合规、运营规则、用户真实行为、异常路径，很多是愿景之外的信息。顶尖 PM 不是从愿景「推出」这些，而是带着愿景去快速验证和修正。

顶尖 PM 的直觉背后是模式库和反馈回路。他看起来一步到位，是因为见过大量案例、做过大量取舍。但即便是顶尖 PM，也会用原型、数据、用户访谈去校准。

所以更准确的说法是：顶尖产品经理能根据愿景得到「判断所有决策的原则和优先级」，但不能得到「所有决策本身」。愿景决定什么值得做、什么优先做、什么不做；具体怎么做，仍然要靠分析、原型和验证。

这一节也在说同一件事：愿景帮你「看清取舍标准」，不替你「画完页面」。

## 动手时，四个维度怎么妥协

真正画的时候，四个维度不是并列 checklist，而是互相约束的决策链。我会排一个妥协优先级：

任务效率 > 可理解性 > 一致性 > 审美

具体动手顺序，我会这样走。

先定信息架构，不是先画视觉。IA 决定任务路径和优先级；它一变，视觉层次必须重排。IA 改了视觉没改，用户还是找不到。

再画状态矩阵，而不是只画正常态。空、加载、错误、禁用、超时、权限不足。状态表先列出来，布局和组件才知道要预留多少空间、文案多长、按钮要不要防重复。

然后做视觉层次，服务任务而不是服务好看。视觉层次是 IA 的视觉翻译：哪个是主任务、哪个是辅助信息、哪个是危险操作。数值应该来自栅格、触控目标和内容密度，不是拆解文章里的固定答案。

最后补微交互，只补状态转换。微交互不是撒糖，是状态变化的反馈：按压、加载、成功、失败、筛选生效、金额变化。它跟着状态矩阵走，不是每个组件都加动画。

落地物也不是一张高保真稿，而是三样东西：任务流/线框、状态表、组件规格。这三样对齐了，四个维度才不打架。

这才是「画」的顺序：先定该画什么，再谈画得是否舒服。

## 一个很小的自查清单

发稿前我会问自己几个问题：

这个页面服务哪个目标、哪个场景、哪个任务？说不出来就是装饰。

主任务是不是一眼可见？危险操作有没有防错？

状态表覆盖了几种？空、加载、错误、超时、权限不足有没有？

信息架构改过之后，视觉层次跟着改了吗？

每个强调色、每个间距、每个动效，能不能回溯到一个关键决策？

注意，可追溯不是每个像素都写论证文档，那会拖死团队。重点是关键决策：主任务、危险操作、异常状态、核心转化路径。

## 最后

用户不会说「我喜欢这个 8px 间距」，但他们会用留存和转化回报那些被认真对待的细节。可细节重要，前提是整体流程、信息架构和核心任务成立。否则就是局部精致、全局低效。

这篇也有折扣：上游常常不全，四维也不是没用——它们是好的「看」法。我反对的不是拆解，是把「看」的工具误当成「画」的起点。

所以我的态度是：学拆解文章的拆解习惯，别照抄它的数字；先把愿景、需求、分析和原型结构钉住，再谈视觉和微交互。顺序不能倒，但回路必须有。

你最近有没有遇到那种「页面挺好看，但就是用起来别扭」的情况？评论区聊聊，我可以按「任务路径—状态—视觉权重—交互反馈」四步帮你拆——这一次，是为了帮你画，不是只为了帮你看。
